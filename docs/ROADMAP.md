# ROADMAP.md — Дорожная карта

## Что реализовано

### Backend

- Полный игровой движок: старт, узлы, выборы, таймауты, финальные узлы
- Защита от гонок через `FOR UPDATE` и проверку `version` сессии
- Серверный таймер (`timer_left_sec`), просрочка влияет на исход
- Идемпотентность `/choice` и `/finish` — повторный запрос не дублирует события
- Аналитика компетенций с рекомендациями (`/analytics/me`, `/analytics/weak`, `/analytics/history`)
- Профиль со статистикой прохождений (`/profile/me`, `/profile/me/sessions`)
- Ачивки с условиями получения
- Уведомления о достижениях
- Лидерборд по общему счёту (fallback на Postgres, если Redis недоступен)
- JWT-авторизация (access + refresh), CORS для фронта
- Docker Compose: `docker compose up --build` поднимает всё одной командой
- Swagger UI / ReDoc для документирования API

### Frontend

- Все экраны: логин, регистрация, список сценариев, проигрывание, дебриф, профиль, ачивки, лидерборд, аналитика
- Восстановление сессии после F5: `GET /node` подтягивает актуальный узел, таймер продолжается
- Таймер от `timer_left_sec`, авто-вызов `POST /timeout` при истечении
- Toast-система: эффекты выборов, speed_bonus, ошибки
- Protected routes, 401 → logout + очистка кеша TanStack Query
- Level и score в хедере
- Дебриф: разбор очков, события, критические решения, ошибки, рекомендации, ачивки
- Идемпотентность на клиенте: кнопки disabled при `isPending`, повторный клик не дублирует запрос
- Пустые состояния, skeleton-загрузка, error с retry — на всех экранах
- Демо-режим (`VITE_DEMO_MODE=true`): длинные дедлайны, предзаполненная сессия, кнопка сброса
- TypeScript strict, без `any`

### Game-Design

- 2 сценария: «Конфликт в вагоне-ресторане», «Медицинский инцидент в пути»
- 6–8 узлов в каждом, нелинейные развилки
- 2 critical-узла с таймером 10–20 сек в каждом сценарии
- Скрытые timeout-выборы на каждом critical-узле
- Достижимы `ending_success` и `ending_fail` в каждом сценарии
- Сбалансированные эффекты: оптимальный путь → шкалы ≥ 60, ошибки → резкое падение
- `debrief_hints` для критических узлов
- 10 ачивок с условиями
- `DEMO_SCRIPT.md` — легенда показа на 3 минуты
- Синтетические данные, соответствие 152-ФЗ

## Что не реализовано

| Область | Функция | Причина |
|---|---|---|
| Backend | Валидатор контента (проверка целостности сценариев при загрузке) | Не хватило времени |
| Backend | Лидерборд на Redis ZSET | Упрощён до Postgres для надёжности |
| Backend | Уровни пользователя (level-up механика) | Не хватило времени, выводится из `total_score` |
| Backend | Внешнее API для HR/LMS с `X-API-Key` | Не в скоупе демо |
| Backend | WebSocket для real-time обновлений | Избыточно для пошагового движка |
| Frontend | Экран `/docs` со встроенным Swagger | Приоритет отдан геймплею |
| Frontend | Мультиязычность (i18n) | Не в скоупе |
| Frontend | Полный E2E-автотест | Ручной чек-лист достаточен для демо |
| Frontend | Анимации переходов между узлами (сложнее fade 150ms) | Избыточно для MVP |
| Game-Design | Третий сценарий | Хватило двух для демонстрации движка |
| Game-Design | Больше развилок (сейчас 2–3 на сценарий) | Достаточно для нелинейности |
| Game-Design | Мультимедиа (звук, видео) | Утяжеляет фронт, cut-list |
| Game-Design | Валидация баланса автотестом | Проверено вручную |

## Дальнейшие шаги

### Backend

1. **Валидатор контента** — при загрузке JSON проверять: все `next_node_key` существуют, есть `ending_success` и `ending_fail`, на `critical` есть `timeout`-выбор, эффекты в диапазонах. Запускать при сиде и возвращать понятные ошибки.
2. **Лидерборд на Redis ZSET** — при росте нагрузки (сотни сессий/мин) вынести топ в Redis, Postgres оставить для холодных данных.
3. **Система уровней** — отдельная таблица `levels`, пороги, награды. Сейчас `level` вычисляется из `total_score`.
4. **Тесты критичных путей** — движок сессии (переходы, эффекты, таймаут), выдача ачивок, идемпотентность.
5. **Внешнее API для HR/LMS** — `X-API-Key`, экспорт прогресса пользователя по запросу.
6. **Аудит безопасности** — rate limiting на `/auth/login`, ротация refresh-токенов, HTTPS-only cookies.

### Frontend

1. **Экран `/docs`** — встроенный Swagger UI через iframe, ссылка в футере.
2. **Аналитика** — развёрнутый экран с графиком прогресса 30 дней (CSS-график или лёгкая либа).
3. **Анимации** — плавные переходы между узлами (slide/fade), анимация изменения шкал, всплеск score при speed_bonus.
4. **Мобильный UX** — оптимизация touch-взаимодействия, кнопки крупнее, таймер компактнее.
5. **Оптимизация** — React.memo на тяжёлых компонентах, lazy-load экранов через `React.lazy`, prefetch сценариев при логине.
6. **E2E-тесты** — Playwright: логин → сессия → выбор → дебриф, проверка таймаута.
7. **i18n** — русский/английский, если проект пойдёт за пределы РФ.

### Game-Design

1. **Третий сценарий** — «Потерянный багаж» или «Ребёнок потерялся в вагоне».
2. **Больше развилок** — минимум 3 пути к `ending_success` в каждом сценарии.
3. **Новые ачивки** — челленджи на комбо-решения, серии без ошибок.
4. **Валидация баланса** — скрипт на Python: прогоняет все возможные пути, проверяет диапазоны эффектов, достижимость концовок.
5. **Обратная связь по компетенциям** — привязать каждый сценарий к компетенциям (`scenario_competencies`), чтобы дебриф показывал, какие навыки тренирует конкретное решение.
6. **Редактор сценариев** — веб-интерфейс для инструкторов: добавлять/менять узлы без правки JSON вручную.

### Совместные задачи

1. **Интеграция контент-пайплайна** — геймдизайнер правит JSON → скрипт валидации → сид в БД → фронт видит новый сценарий без пересборки.
2. **Аналитика компетенций** — backend считает по `scenario_competencies`, frontend отображает в профиле и дебрифе, геймдизайн проставляет веса.
3. **Мониторинг** — логирование ошибок игрового движка (Sentry или аналог), чтобы видеть, где игроки «застревают».
4. **Формирование пилота** — собрать 3–5 проводников, прогнать все сценарии, собрать обратную связь, доработать баланс.
